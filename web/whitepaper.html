Technical White Paper — v0.3.1

MIKA5: local-first AI
for the individual

A technical document on how MIKA5 Community v0.3.1 is built: what runs on your machine, what only leaves it when you authorize it, and what does not exist yet.

Version 0.3.1 · November 2026 License: AGPL-3.0 Platform: Windows · macOS · Linux

Abstract

Language models have become widely available, but access to them is largely mediated by proprietary cloud platforms that impose subscription costs, data disclosure and usage policies. MIKA5 proposes a different arrangement: an Electron desktop application that runs open-weight models on local hardware through Ollama, keeps its memory in a local SQLite database, grounds answers with a local retrieval-augmented generation engine, and treats cloud providers as an optional path that is only taken after the user selects one and authorizes what will be sent. This document describes the architecture of MIKA5 Community v0.3.1 as it is implemented, states explicitly what belongs to a future edition, and cites the source file behind each technical claim so that any reader can verify it against the published tag.

Scope of this document: everything described in sections 1 to 10 is implemented in Community v0.3.1 unless the text says otherwise. Section 11 separates what exists from what is planned. Claims about behaviour reference the source file that implements them, at tag v0.3.1.

Section 1

The problem with cloud-first AI

The AI industry has converged on cloud delivery as its primary distribution mechanism. Users reach language models through web interfaces, mobile applications and APIs, all of which route every prompt and every response through remote servers operated by a small number of companies. That arrangement works, and for many people it is the right trade. It also introduces structural consequences that fall hardest on individuals, small organisations and users in regulatory environments that differ from the vendor's.

When you type a thought into a hosted assistant you are not only using a service. You are handing over content under terms that the other party can change, and that you did not write.

Subscription dependency. Cloud access is priced per token, per month or per call. Sustained professional use therefore depends on continuous payment, and the terms of that payment are set by the vendor. Models that were free during a preview become paid; tiers are restructured; capabilities move behind higher plans. A workflow built on a hosted model inherits the vendor's pricing decisions.

Data disclosure. A prompt sent to a hosted API leaves the machine and is processed in plaintext on the receiving server. Transport encryption protects the journey, not the destination. Terms of service for several providers reserve the right to use interactions for model improvement, safety monitoring or abuse detection. For medical records, legal documents, business strategy or private correspondence, that disclosure may carry regulatory weight of its own.

Policy enforcement. Hosted models apply the content policies of the company running them. Those policies change over time and vary by region, and they can block legitimate professional work: a researcher studying extremist rhetoric, a security engineer testing prompt injection, a novelist writing difficult material. When the model runs locally, the user and their system prompt define the behavioural envelope.

Infrastructure dependency. Hosted services have outages, change behaviour between model versions and retire models. A workflow tuned to one version can break when it is replaced. Local weights, once downloaded, are stable: the same file produces the same behaviour regardless of connectivity or vendor decisions.

Section 2

Open-weight models as the base layer

MIKA5 is built on the premise that open-weight language models are now capable enough for a large share of everyday work. This document publishes no benchmark scores and makes no ranking claims: reported numbers move with quantization, prompt format, sampling parameters and evaluation harness, and a figure that cannot be traced to the exact build you are running does not support a decision. The Model Guide lists the models MIKA5 can run today with their verified sizes and hardware requirements; each model card documents its own evaluations.

The argument for open weights does not rest on comparative scores. Open models can be inspected, because the weights are published and the architecture is documented. They can be fine-tuned on domain data without asking permission. They can be run at the quantization level the hardware allows, trading quality for speed. They can be used in environments with no outbound connectivity at all. And they cannot be repriced, restricted or withdrawn by a decision the user has no part in.

The ecosystem is also plural, which matters more than any single model. Meta publishes Llama under a licence permitting commercial use. Alibaba publishes Qwen with broad multilingual coverage, Spanish included. DeepSeek publishes reasoning models trained with reinforcement learning. Mistral brings European research and European language coverage. BigCode publishes StarCoder trained on a corpus with an opt-out policy for repository owners. No single organisation controls that set.

MIKA5 treats open-weight models not as a fallback for when cloud access fails, but as the default path between the user and the machine.

Ollama provides the local runtime. It exposes a uniform HTTP API over GGUF models, handles quantization and memory allocation, and listens on 127.0.0.1:11434. MIKA5 speaks to it over that loopback address. Adding a model is a single ollama pull and requires no change to the application. When a locally installed model is selected and no cloud inference is used, the whole path from keystroke to answer stays on the machine: the renderer, the main process, the local SQLite file and the Ollama server.

Section 3

System architecture

MIKA5 is an Electron desktop application with a two-process split, built from a single codebase for Windows, macOS and Linux. The main process runs in Node.js and performs every privileged operation: reading and writing the database, touching the file system, talking to AI providers, encrypting credentials and indexing documents for retrieval. The renderer process draws the interface and nothing else.

The main window uses contextIsolation: true, nodeIntegration: false and sandbox: true, defined in src/main/window-security.js. Its sandboxed preload exposes the window.mika5.* bridge. Privileged IPC handlers accept only the main frame of a registered application window loading the local renderer. These controls limit renderer access; they do not replace input validation or guarantee the absence of vulnerabilities.

The offscreen window used for PDF export is a separate case: it is created with sandbox: true (src/main/print-export.js). It renders a fixed local template and needs no privileged access, so it runs under the stricter setting.

The renderer also carries a Content Security Policy declared in src/renderer/index.html. Its connect-src 'none' directive is the operative part: the interface cannot open network connections of its own. Every request to a model, local or remote, is made by the main process after crossing the IPC boundary, where the input is validated. If an injection ever executed inside the renderer, it would find no network path and no file system from there.

Persistence uses better-sqlite3, a synchronous binding. Synchronous access removes a class of race conditions that arises when several asynchronous writes interleave, and SQLite itself provides transactions and a single portable file. The alternatives were rejected for concrete reasons: browser storage offers no durable file the user can copy, and a networked database would require running a server and would break the property that the application works with no network at all.

Packaging is produced by electron-builder: NSIS installer and portable executable for Windows, DMG and ZIP for macOS on Apple Silicon and Intel, and AppImage, DEB and RPM for Linux. That is nine installers per release. Section 10 describes what else is published alongside them and how to verify it.

Section 4

Privacy model

The privacy model rests on four statements, each written to be checkable: local by default, cloud only on explicit authorization, content is not rewritten and credentials are encrypted at rest.

Local by default. MIKA5 stores conversations in local SQLite and indexes documents on the device. Locally installed Ollama models and llama.cpp provide local inference. Ollama can also route to cloud models; MIKA5 classifies those requests as cloud and requires explicit consent before sending the selected data. Community has no MIKA5-operated inference, telemetry, account or automatic update service.

Cloud only on explicit authorization. This document avoids the absolute phrasing used in earlier versions. It is not true that data never leaves the machine, and it is not true that MIKA5 makes zero outbound requests: the moment you configure a provider and send a message, a request goes to that provider, and features such as fetching a provider model catalogue or downloading a generated image are outbound requests too. What is true is that none of it happens until you select a cloud provider and authorize the scope. Before the first send under a given scope, a dialog lists the categories that will leave the device — message, conversation history, project instructions, text attachments, images and retrieved RAG context. Consent is stored under a versioned key scoped to one provider and one project, and can be revoked from the actions menu (src/renderer/cloud-consent.js).

The provider's terms then apply. Once a request reaches a third party, that company's retention, logging and content policies govern what happens to it. MIKA5 cannot alter that and does not claim to. Authorizing a cloud provider is a decision with consequences the application cannot undo; the consent dialog exists so that the decision is made deliberately and with the payload in view.

Content is not rewritten. MIKA5 performs no automatic redaction of personal data. There is no step that replaces an email address, a phone number or an identifier with a token, and there is no anonymisation layer. Earlier versions of this white paper described such a step; it does not exist and the project has decided it will not exist by default. In v0.3.1 the provider manager sets sanitization off and passes that setting to every adapter, so what the consent dialog lists is what is transmitted, byte for byte. Any redaction added later must be opt-in, visible and auditable, precisely so that a silent transformation can never change the meaning of a document, a log or a block of code.

Credentials are encrypted at rest. An API key is encrypted with AES-256-GCM before it reaches the database (src/main/ai-providers.js). The key material comes from Electron's safeStorage, which delegates to the operating system credential store — DPAPI on Windows, Keychain on macOS — so a copied database file is not enough to recover the key without the same user session. If protected safeStorage is unavailable (including Linux basic_text), credentials work in memory for the current session only. Successfully decrypted legacy records are migrated to protected storage when available; otherwise their database value is cleared after loading them into session memory. GCM authentication tags mean a corrupted or tampered record fails loudly instead of decrypting into plausible nonsense.

The cloud is not forbidden. It is disclosed, itemised and revocable — and it stays off until you turn it on.

Section 5

The RAG engine

A language model is trained on a fixed corpus and knows nothing about your documents. Retrieval-augmented generation closes that gap by finding the passages of your own material that relate to the question and putting them in front of the model before it answers. In MIKA5 the whole pipeline runs on the machine: the documents, the vectors and the search.

The constants below are the ones in src/main/rag.js at v0.3.1, not illustrative values.

  1. 1. Chunking. Document text is split into chunks of 4,200 characters with a 700-character overlap (CHUNK_CHARS, OVERLAP_CHARS). The overlap keeps an idea that straddles a boundary present in both neighbouring chunks, so a sentence that begins near the end of one also appears near the start of the next.

  2. 2. Embedding. Each chunk goes to the Ollama embedding endpoint using nomic-embed-text by default, or another installed embedding model. The result is a floating-point vector whose dimensionality is a property of the chosen model, not of MIKA5: change the model and the vector width changes with it.

  3. 3. Storage. The chunk text and its vector are written to knowledge_chunks as a serialised Float32 blob. A foreign key links each chunk to its knowledge_items row, and an optional chat_id column scopes it to a single conversation.

  4. 4. Query. When a message is sent, the query text is embedded with the same model and compared against the stored vectors by cosine similarity. The default is the three closest chunks (TOP_K_DEFAULT = 3), and the caller may ask for a different number, which the engine clamps to between 1 and 10. The selected chunks are injected into the conversation as a system message before the model is called.

Vectors are cached in memory per scope with a five-minute time to live (CACHE_TTL_MS), so repeated questions inside a session do not reload embeddings from SQLite. An expired entry is refetched, which is also how a newly indexed document becomes visible to retrieval without restarting the application.

Scope is part of the design rather than a setting. The cache key is built from the project, the chat and whether project-level documents are included (scopeKey in rag.js), which is what keeps knowledge bases from bleeding into each other: a document attached to one conversation is retrieved in that conversation, project documents are retrieved across the project, and Quick Chat keeps its own. Two chats can hold contradictory reference material without either one contaminating the other.

Section 6

Provider architecture

Every backend sits behind one interface. The renderer only ever calls window.mika5.ai.chat() and does not know whether the request will end at a local Ollama server or a remote API. Routing decisions therefore live in the main process, where they can be audited, and the interface has no influence over them.

v0.3.1 implements seven adapters registered through src/main/provider-registry.js, with implementations in src/main/providers/: Ollama supports local and cloud models; llama.cpp provides local inference; OpenAI, Anthropic, Groq, Moonshot and Alibaba Cloud Model Studio are optional cloud providers. Model catalogues depend on provider configuration and account access.

Capabilities are declared, never guessed. src/main/provider-capabilities.js holds one contract per provider stating what its adapter actually implements — chat, vision, image generation, tool use, streaming, usage reporting and whether its model catalogue is configurable. The rule the module enforces is that MIKA5 never infers a capability from a model name at runtime. Earlier versions of this document described a name-based fallback for vision detection; that fallback is precisely what the module exists to prevent, and it is not how v0.3.1 behaves.

Vision is resolved by a policy per provider. Ollama uses probe: the backend itself is asked through /api/show whether the selected model accepts images. OpenAI and Anthropic use allowlist: a hand-curated list kept in the module, where adding an entry is an explicit statement that the model was verified against that adapter's API. Alibaba uses catalog: the configurable catalogue declares the capability per model. Groq and Moonshot are marked pending — the transport exists but no model is verified, so MIKA5 refuses an image attachment there instead of silently dropping it and letting the model answer as if the image had never been sent. llama.cpp is none: that adapter does not carry images at all.

Multimodal routing. When a conversation involves images, MIKA5 separates two different operations: analysing an image the user attached, and generating one. Generation is reached through a single internal tool, generate_image, executed in the main process for the providers whose contract declares image generation. It is not a general agent loop and there are no user-defined tools in Community v0.3.1; the only tool the model can invoke is that one.

Attachments and visual context. Images attached to a message are transported for that request. They are not accumulated into a persistent visual memory that silently follows the conversation, which matters for the consent model: what the dialog itemises for a send is what that send carries.

Cancellation. Every in-flight request is registered under a validated identifier in src/main/request-registry.js, which rejects a malformed or duplicate identifier and holds an abort controller per request. Stopping a generation aborts the underlying request rather than merely hiding the result, so a cancelled cloud call stops consuming tokens and a cancelled local call releases the model.

Section 7

Data model and portability

Everything lives in one SQLite file in the application userData directory — on Windows, %AppData%\Roaming\mika5-desktop\mika5.db. It is an ordinary file: you can copy it, back it up, inspect it with any SQLite tool and move it to another machine without asking anyone for an export.

The schema in src/main/db.js declares six tables — five that hold user content, plus app_state for interface preferences.

projects — the top-level unit, with a name, description, optional icon and colour, and a system_prompt that shapes the assistant inside that project. A reserved project acts as the home for conversations that do not belong to a user-created one.

chats — conversation threads inside a project, each with a title, an optional per-chat system_prompt that overrides the project one, and a timestamp. Foreign keys with ON DELETE CASCADE mean deleting a project removes its chats rather than leaving them stranded.

messages — role, content, the model that produced the message, optional images and an optional reference to the message being answered. Storing the model per message is what lets the interface label each answer and mark the point where the model changed mid-conversation.

knowledge_items — one row per document, with title, MIME type, content, an optional chat_id for per-chat scoping and an index_status that moves from pending to indexing to ready. A document that cannot be indexed, typically because no embedding model is installed, lands in an error state and can be retried instead of failing silently.

knowledge_chunks — the retrieval table described in section 5: chunk text, embedding blob, link to the parent document and optional chat scope, with cascading deletes so that removing a project or a chat takes its vectors with it.

The connection runs with PRAGMA journal_mode = WAL and PRAGMA foreign_keys = ON. Both are deliberate and neither is a SQLite default: write-ahead logging lets background indexing proceed while a conversation is being read, and foreign key enforcement is what makes the cascade rules above real rather than decorative.

Export. A conversation can be written out as Markdown, plain text, HTML, a Python file or PDF. The first four are produced directly from the stored messages; the PDF is rendered by the sandboxed offscreen window described in section 3. Export exists so that leaving MIKA5 costs nothing: the database is already a portable file, and the exports cover the formats a document is normally handed on in.

Section 8

Security design

The threat model this section addresses is ordinary rather than exotic: content authored elsewhere arrives in the application — a model response, a downloaded image, a document — and must not be able to act on the machine. Alongside that, credentials on disk must survive the theft of the database file, and the interface must not be able to open network paths of its own.

Process boundary. As stated in section 3, the main window runs with context isolation and sandboxing on and Node integration off. The preload script defines the entire surface the interface can reach, and each IPC handler validates its input before touching the database or the file system. The value of the boundary comes from how narrow that surface is, alongside sandboxing and IPC sender validation.

Content Security Policy. The renderer declares default-src 'self' with connect-src 'none', and closes off object-src, frame-src, base-uri and form-action. The interface cannot connect anywhere, cannot embed a frame and cannot submit a form to a remote endpoint.

Rendering untrusted Markdown. Model output is Markdown that may contain HTML, and it is not trusted. It is parsed and then sanitised with DOMPurify, vendored into the application rather than fetched from a CDN, and applied with an explicit allowlist plus a hook that inspects attributes after sanitisation. Sanitising with a real parser rather than a regular expression is the difference between removing a script tag and removing every path that executes. Code blocks are highlighted after sanitisation, never by injecting raw HTML.

Input validation. Identifiers arriving over IPC are checked before use. Project and knowledge identifiers must match the expected pattern, so a value carrying path traversal characters is rejected with an explicit error rather than reaching a file operation. The application state table accepts only keys from an allowlist, which keeps the state API from becoming a general-purpose write primitive.

Guarded downloads. Fetching a generated image is an outbound request driven by content the application did not author, so src/main/network-security.js constrains it: the address is resolved and checked against private and loopback ranges to prevent the application from being pointed at the local network, redirects are followed only for the expected status codes and only within limits, the response is capped in size, and the image type is confirmed from the bytes rather than trusted from a header or a file extension.

Outbound links. Window-opening is intercepted so that an external link is handed to the operating system browser instead of opening an Electron window that would render remote content inside the application.

Credentials. Described in section 4: AES-256-GCM with key material from the operating system credential store through safeStorage, with session-only credentials when protected storage is unavailable.

Engineering practice, not a user feature. The Electron test suite runs against a unique temporary userData directory created per run, and discards any externally supplied path. This is a property of how the project is tested, not something a user configures: it exists so that running the tests can never read, corrupt or delete a real installation database, and so that a passing suite means the same thing on a developer machine as in continuous integration.

Section 9

llama.cpp — a second local runtime

Ollama is the primary local runtime, but some users prefer llama.cpp directly: it exposes the quantization parameters, hardware acceleration flags, batch sizes and loading behaviour that a managed runtime deliberately hides. For someone who keeps one model resident instead of switching between several, it also carries slightly less overhead.

The llama.cpp server exposes an OpenAI-compatible HTTP API on http://127.0.0.1:8080/v1, so the adapter reuses the same request shape as the OpenAI provider without model-specific code. The adapter is implemented in v0.3.1 and is selected as llama.cpp (Local) in the provider list; it probes for a running server at startup.

# Build llama.cpp

$ git clone https://github.com/ggerganov/llama.cpp && cd llama.cpp

$ make # or cmake, for GPU support

# Obtain a GGUF file yourself

$ ./llama-server -m model.gguf --port 8080 -ngl 99

# Then pick llama.cpp (Local) in MIKA5

MIKA5 detects the running server and lists its models

Two differences are worth stating plainly. First, llama.cpp does not manage downloads: obtaining the GGUF file and pointing the server at it is the user's responsibility, where ollama pull would have done it. Second, MIKA5 does not send images to this adapter. Its capability contract declares no vision support, so an image attachment is refused with a visible message. llama.cpp itself can serve multimodal models with the appropriate build; the limitation described here is MIKA5's adapter, and it is stated as a refusal rather than a silent omission.

Section 10

Licence, distribution and verification

MIKA5 Community is published under the AGPL-3.0. The licence is the one in LICENSE at the root of the repository and the one declared in the package manifest. Under the AGPL the corresponding source of the version you run must be available to you, which is why every release publishes a source archive next to the installers rather than only the binaries.

The v0.3.1 release publishes fifteen assets: nine installers — two for Windows, four for macOS across Apple Silicon and Intel, three for Linux — plus the source archive, LICENSE, BUILDING.md, COMMUNITY.md, a build metadata file recording the commit the release was built from, and SHA256SUMS.txt.

SHA256SUMS.txt contains fourteen entries, one for each of the other fourteen assets. The difference is not an omission: a checksum file cannot contain its own hash, because writing the hash into the file would change the file and invalidate it. Coverage is therefore complete — every asset that can be verified against the list is on the list.

The repository also carries SECURITY.md for reporting vulnerabilities, TRADEMARK.md for the name and marks, BUILDING.md for reproducing a build from source, and COMMUNITY.md for participation. The AGPL covers the code; the trademark document covers the name, and the two are deliberately separate.

There is no automatic updater in Community v0.3.1. Nothing checks for a new version in the background and nothing installs one: updating means downloading a release yourself. That is a smaller feature set, and it is also one fewer channel that talks to a server on your behalf.

Section 11

Editions and roadmap

This section exists to keep the rest of the document honest. Everything above describes Community v0.3.1 as implemented. Everything below is either planned or absent, and is labelled accordingly. Nothing in the roadmap is available today, and no date or price is promised for any of it.

MIKA5 Community

Available — v0.3.1

The desktop application described in this document, under AGPL-3.0. Local execution through Ollama or llama.cpp, projects and chats, local knowledge base and RAG, optional cloud adapters configured with your own key, explicit and revocable consent, export, and the security design of section 8. This is the only edition that exists.

MIKA5 Pro

Planned — in development

A future edition of separate components aimed at advanced use. It does not exist in v0.3.1, no part of it ships in this release, and this document names no price and no date. Any capability attributed to Pro elsewhere should be read as intent, not as a feature you can use.

MIKA5 Cloud

Planned — in development

A future managed service. Synchronisation between machines, accounts, backups, remote agents and continuous execution are concepts belonging to that edition. None of them exists in Community v0.3.1: there is no account system, no synchronisation and no server operated by MIKA5 that your installation talks to.

Delivered in Community v0.3.1 and available today:

Three platforms from one codebase. Implemented in v0.3.1 Windows, macOS and Linux built by the same pipeline on every version tag, with nine installers per release.

Explicit and revocable cloud consent. Implemented in v0.3.1 A versioned consent scoped to one provider and one project, itemising what leaves the device before the first send.

Declared provider capabilities. Implemented in v0.3.1 One contract per adapter and five vision resolution policies, so an image attachment is refused where it is not verified rather than dropped in silence.

Text and visual routing. Implemented in v0.3.1 Image analysis and image generation are separated, the latter through the single internal tool described in section 6.

Cancellation of a request in flight. Implemented in v0.3.1 Stopping a generation aborts the underlying request instead of hiding its result.

Knowledge scoped by project and chat. Implemented in v0.3.1 Documents attached to one conversation are retrieved only there, and Quick Chat keeps its own base.

Export in five formats. Implemented in v0.3.1 Markdown, plain text, HTML, Python and PDF, the last one rendered by the sandboxed offscreen window.

Planned for future Community releases, none available today:

Token streaming. Planned Delivering tokens as they are generated instead of the whole answer at once, so a long response can be read and interrupted early. It requires moving that path from a single IPC call to a stream of events.

Drag and drop for documents. Planned Adding files to the knowledge base by dropping them, instead of going through a file dialog.

User-defined tools. Planned Community v0.3.1 exposes exactly one internal tool, the image generation described in section 6. A general agent loop over user-defined tools — search, calculation, file access — is a different problem, and the part that needs designing is the execution sandbox, not the model plumbing.

Hybrid retrieval. Experimental Retrieval today is pure cosine similarity over dense vectors. Combining it with keyword search would help with proper nouns and technical terms that a dense vector blurs. SQLite ships a full-text extension, so this needs no new dependency, but it is unevaluated.

Model management interface. Planned Browsing, downloading and removing models from inside the application. Today that is done with the Ollama command line.

Knowledge base export and import. Planned Moving an indexed knowledge base between machines with optional encryption. Conversation export already exists; this is about the vectors.

Query routing across models. Experimental Sending a question to a specialised model according to its type. v0.3.1 routes between text and visual operations, but does not classify a question in order to pick a chat model for it.

Plugin system. Planned A sandboxed extension surface for third-party tools, providers and panels.

Synchronisation between machines. Not included in Community Encrypted replication of projects and conversations belongs to the Cloud edition. It does not exist, and if it is ever built it will be opt-in and disclosed, never on by default.

Mobile client. Not included in Community There is no mobile application. MIKA5 v0.3.1 is a desktop application for Windows, macOS and Linux, and nothing else is published.

Remote or continuous agents. Not included in Community Nothing in v0.3.1 runs without you: there are no background agents and no scheduled execution. Such capability would belong to the Cloud edition.

Team collaboration. Not included in Community There are no accounts, no shared workspaces and no permissions. The database is single-user by design.

Server-side runtimes such as vLLM. Not included in Community vLLM is not part of Community v0.3.1 and there is no adapter for it. It appears here only as possible infrastructure for a future Pro or Cloud edition, which is a different product from the desktop application this document describes.

Section 12

Conclusion

The thesis of MIKA5 is that an AI tool should work for the person using it rather than collect from them. Open-weight models have reached the point where that is a practical arrangement for a large part of everyday work, and the remaining difficulty is not capability but architecture: where the data sits, who decides when it moves, and whether the answer to that question can be checked instead of trusted.

The choices in this document follow from that. Open models at the core. SQLite as the memory, in a file you own. A retrieval engine that indexes your documents on your machine. Cloud access available, itemised and revocable, without pretending it is risk-free once authorized. And a security design stated precisely enough to be contradicted: this document names the file behind each claim, including the main window isolation and sandbox settings.

A document that only lists what works is marketing. What makes a technical document useful is that it also states what does not exist, and where the boundary lies.

Earlier versions of this white paper claimed automatic redaction of personal data, a sandboxed renderer and the absence of any outbound request. None of those was accurate. They have been removed rather than softened, and the sections above say what the code does instead. Correcting a specification is cheaper than letting someone rely on it.

This is version 0.3.1. It is a working desktop application, not a finished product, and section 11 marks the line between the two.
